# E-Commerce API (Engineering Task 1)

This project is a versioned, consumable RESTful E-Commerce API built with Express, Node.js, TypeScript, and Prisma (PostgreSQL). 

It serves as the backend infrastructure for a digital storefront or retail platform, providing complete lifecycle management for inventory, users, and sales transactions.

## Resources

The API exposes five core related resources representing the fundamental business entities of an e-commerce platform:

*   **Categories**: High-level classifications used to group related merchandise.
*   **Products**: The actual sellable inventory items, belonging to exactly one Category.
*   **Customers**: The registered end-users capable of placing orders.
*   **Orders**: Transactional records representing a customer's purchase event.
*   **Order Items**: The granular line-items linking a specific Order to specific Products, including historical pricing and quantities.

## Base URL

All requests must be routed through the versioned API base path:

```
/api/v1/
```

Versioning ensures that future breaking changes to the API architecture (e.g., `/api/v2/`) can be introduced without disrupting existing mobile or web consumers seamlessly interacting with the `v1` namespace.

## API Endpoints

The API supports full CRUD behaviors across all five resources via standardized HTTP methods. 

### Categories

#### `GET /api/v1/categories`
*   **Purpose:** Retrieve a paginated list of categories.
*   **Query Parameters:**
    *   `limit` (String, Optional): Number of records.
    *   `offset` (String, Optional): Pagination offset.
    *   `sort` (String, Optional): Field to sort by.
    *   `order` (String, Optional): Sort direction.
    *   `name` (String, Optional): Partial text match on category name.
    *   `createdAfter` (String, Optional): ISO date string filter.
*   **Response Status:** 200 OK
*   **Example Request:**
    ```bash
    curl "http://localhost:3000/api/v1/categories?limit=2&sort=name&order=asc"
    ```

#### `GET /api/v1/categories/:id`
*   **Purpose:** Retrieve a single category by its ID.
*   **Response Status:** 200 OK (or 404 if not found, 400 for bad UUID)
*   **Example Request:**
    ```bash
    curl "http://localhost:3000/api/v1/categories/123e4567-e89b-12d3-a456-426614174000"
    ```

#### `POST /api/v1/categories`
*   **Purpose:** Create a new category.
*   **Request Body:**
    *   `name` (String, Required)
    *   `description` (String, Optional)
*   **Response Status:** 201 Created (or 422 for invalid body)
*   **Example Request:**
    ```bash
    curl -X POST "http://localhost:3000/api/v1/categories" \
    -H "Content-Type: application/json" \
    -d '{"name": "Electronics", "description": "Gadgets"}'
    ```

#### `PATCH /api/v1/categories/:id`
*   **Purpose:** Update an existing category (must include at least one valid field).
*   **Request Body:** 
    *   `name` (String, Optional)
    *   `description` (String, Optional)
*   **Response Status:** 200 OK

#### `DELETE /api/v1/categories/:id`
*   **Purpose:** Delete a category. Fails safely (400) if products are currently attached to it (foreign key constraint).
*   **Response Status:** 204 No Content

## Pagination

Every list endpoint utilizes strict, consistent limit/offset pagination logic via query parameters:

*   **`limit`**: Limits the number of records returned. 
    *   Default: `20`
    *   Maximum: `100` (oversized requests are automatically and safely clamped to `100` rather than crashing the database).
*   **`offset`**: Number of records to skip.
    *   Default: `0`
    *   Invalid values (e.g. negative offsets) are explicitly rejected with an **HTTP 400 Bad Request**.

## Filtering

Each resource exposes targeted filtering via URL query parameters. Text-based string filters utilize case-insensitive partial matching (`contains` in Prisma), whereas relational references (UUIDs) and Enums utilize exact deterministic matching.

| Resource | Filter Parameter | Type | Behavior | Example |
| :--- | :--- | :--- | :--- | :--- |
| **Categories** | `name` | String | Partial Match | `?name=electronics` |

## Sorting

You can dynamically sort collection lists using the `sort` and `order` query parameters. 
Invalid sorting fields or directions are strictly rejected with an **HTTP 400 Bad Request**.

*   `sort`: The exact field name to sort by (e.g., `price`, `createdAt`, `name`). This varies by resource.
*   `order`: The sort direction. Allowed values: `asc`, `desc`.

**Example:**
```bash
curl "http://localhost:3000/api/v1/products?sort=price&order=desc"
```

## Rate Limiting

The API operates unauthenticated. To safely guarantee service availability and defend against abuse or DDOS attacks, strict IP-based rate limiting is globally enforced across all routes.

*   **Limit:** `100` requests
*   **Window:** per `60` seconds (per IP address)

Requests exceeding the threshold are cleanly aborted with an **HTTP 429 Too Many Requests** status code, returning the standard error envelope and a standard HTTP `Retry-After` header indicating exactly when the client is permitted to resume traffic.

Configuration thresholds are environmentally driven (`RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_MS`) and cleanly segregated from the individual route controllers.

## Consistent Envelopes

### Success Envelope

All paginated collection endpoints systematically wrap datasets in a standardized JSON payload:

```json
{
  "data": [
    { ...record }
  ],
  "meta": {
    "total": 400,
    "limit": 20,
    "offset": 0,
    "hasMore": true
  }
}
```
Non-paginated endpoints (e.g. GET `/id`, POST, PATCH) return the direct object as an unwrapped JSON structure, providing clean and idiomatic developer consumption.

### Error Envelope

All API errors (Validation, 404, Runtime, or Rate Limits) are intercepted centrally and mapped into a consistent, predictable envelope structure. This permits reliable client-side error decoding:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Human readable message"
  }
}
```

#### Documented Error Scenarios
*   **HTTP 400 Bad Request:** Malformed query inputs, invalid limits, bad sort parameters, malformed UUID path parameters.
*   **HTTP 404 Not Found:** Supplied ID is a valid UUID but the resource does not exist in the database.
*   **HTTP 422 Unprocessable Entity:** POST/PATCH body structural/type validation failure (e.g., missing required fields, unknown schema fields, or empty updates).
*   **HTTP 429 Too Many Requests:** IP rate limit exceeded.

## Setup and Running Locally

Ensure PostgreSQL and Node.js are successfully installed on your machine.

1.  **Install dependencies:**
    ```bash
    npm install
    ```
2.  **Configure environment:** Duplicate `.env.example` into `.env` and fill the variables.
3.  **Prepare database:** Push the Prisma schema to the database.
    ```bash
    npx prisma db push
    ```
4.  **Seed the database:**
    ```bash
    npx prisma db seed
    ```
5.  **Start the development server (Hot-reload enabled):**
    ```bash
    npm run dev
    ```
6.  **Build for production (TypeScript compile):**
    ```bash
    npm run build
    ```

## Design Decisions

*   **Why these resources?** Categories, Products, Customers, Orders, and Order Items form a globally understood, highly normalized transactional foundation for digital storefronts. This separates inventory tracking from relational ownership workflows.
*   **Generated Identifiers:** UUIDs (Universal Unique Identifiers) were employed instead of sequential numerical IDs. This securely masks business velocity (preventing scraping/guessing of order volume) while ensuring data remains strictly collision-free if partitioned or migrated.
*   **Pagination Choice:** Standard limit/offset pagination was implemented. It offers intuitive backward-forward page jumps for generic administrative interfaces, and is performant for realistically-scaled tables.
*   **Response Envelope:** Structuring collections under `{ data, meta }` guarantees the payloads are self-describing. Mobile and web front-ends immediately understand the pagination state natively. Similarly, a centralized error format standardizes crash-recovery UX parsing.
*   **Versioned API (`/api/v1`):** Mandating a strict `v1` prefix shields deployed mobile/web clients from abrupt crashes if structural routing conventions or model designs are heavily refactored down the road (`v2`).
*   **Rate Limiting:** Unauthenticated public platforms are incredibly vulnerable to automated scraping, parameter guessing, and brute-force traffic bursts. Rate-limiting strictly guards database I/O overhead.
